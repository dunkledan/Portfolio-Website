Escape the Labrynth is a 2D puzzle game written using the Unity Game Engine. The player is a shapeshifting character attempting to escape a laboratory. The game has 4 levels, with each of the first 3 focusing on introducing 1 or 2 specific mechanics and building on the previous levels with fairly simple puzzles and the final level combining all previous mechanics.


The player has 3 shape states, stored in an animator component for smoother animations. This code accesses determines this state when the shapeshift input is pressed. Each state also has different abilities and this function handles which is active and other relevant properties for that state.


The shooting mechanic works using a combination of 4 different classes: the player bullet and lever class. The Player handles an input to decide where to fire and which direction to fire a bullet instance. The bullet class handles its own life time and the lever class detects a bullet instance collision to open a given door using the door class to handle the properies of the door.

The climbing mechanic handles scene changes between different layers of a given level. This mechanic is used for interesting puzzles to avoid enemies or get to inaccessable sections of the game. This uses coroutine timers to determine climbing time and ensure the player does not move when climbing. The ladder class also sets the animator state machine to be in the climbing state when appropriate to handle animation and other properties of different states where appropriate.

The enemy AI in this game uses a 2D nav mesh to determine paths that enemies can walk on. There are 3 different types of enemy in the game so far including the base enemy. These enemies include a patrol behaviour, a patrol and chase behaviour, and a patrol and shoot behaviour. The patrol And enemy classes are only able to see the player with line of sight in a radius, this is achieved using raycasting between the player and enemy to make sure the line of sight is appropriately used. The patrolling behaviour uses 2 target points for the enemy to patrol between which can be expanded for as many patrol points as required.



The background tiles for this game are procedurally generated. This is done using unity rule tiles on a tile map and the perlin noise function with sample values to determine the specific tile that should be place at a given point. This was an interesting problem to solve as it was far more mathematical than most other mechanics for this project.

Military Defence is a top down 3D tower defence game built using Unreal Engine 5. It was created using a framework provided by my university, originally with a goal of creating a level prototype, however I designed this game to be very expandable in a similar way to other tower defence games rather than being level focusd. this version features 3 rounds with unique enemies and a fairly well balanced scoring system to gain upgrades and towers.

Shooting functions using a combination of two major blueprints handling two different aspects of the shooting mechanic. The weapon controller blueprint for a given weapon creates an instance of a bullet blueprint class when appropriate with a velocity position and rotation dependant on where the player and thier mouse is. The projectile Blueprint class itself handles its own audio, particles and lifespan and damage to other actors in the scene to create the bullet hitting effect.


Tower placement was one of the most complex mechanics in the game, requiring interaction between UI elements, different world scene actors, the score system and appropriate mouse raycasting. The system works by spawning a new instance of the bought tower if the player has the correct amount of currency, at this point a new tower instance is continously kept on the mouse position on the nearest object on the screen until the left click button is pressed to place the tower, at which point the towers will begin to shoot at the closest enemy to them that is in range determined by a large trigger collision box.


Military defence has three types of enemies, each with unique behaviours and stats. Enemies all inherit from the base enemy class to allow all enemies to follow a navigation path for the level and take some amount of lives upon reaching the end of the track. These enemies appear at different points throughout the rounds, increasing in difficulty as the game goes on until the final boss round where all enemy types will be spawned. The second round enemies have the ability to aim at and shoot the player for an extra level of difficulty, the boss has inflated health and spawns both types of enemies on a timer until defeated or killing the player. The blueprints for all of these mechanics are shown below.


Military Defence features 3 rounds consisting of different enemy waves and increasing difficulty. Each round uses a spawning timer to spawn a set amount of a set enemy class instance at the start of the track which navigate to the end of the track. When the final enemies are spawned the round number is incremented and enemies stop spawning. The first round blueprint logic is below.


The health over time mechanics in Military defence involve blueprint class isntances that deal damage or heal the player in intervals using timers. These times and amount healed in that time is editable and is used for lava and a healing pool within the level.


The shop system is used to allow the players to gradually become more powerful by purchasing new towers and weapons. Currency is collected by killing enemies each round wit heach enemy having a set score asociated with it. The shop can then be used to purchase these weapons only when the player has enough money. If the purchase is a tower the tower system is utilised (See Tower Placement section) otherwise a weapon pickup is spawned next to the shop terminal for the player to pick up.

This orbit simulation was created to understand the principles of the fixed function pipeline for graphics program using C++, OpenGL 1.0 and FreeGLUT. The simulation features code to load RAW and TGA formatted texture files, load standard triangle OBJ files, scene lighting, important scene data structures, specific object selection and manipulation in the scene and dynamic user controlled movement.


The camera system in this project is fairly standard using WASD to alter the Eye Centre and Up values of a camera class which GLUT uses to look at the correct position. This created a smooth sense of camera movement throughout the world, however to give more control I also implimented mouse movement to look in an appropriate direction, using some more complex mathematical formulas to calculate angles based on a 2D mouse screen position.


The Object Loader takes OBJ files and converts them into a format that can be used by the rendering engine. This is not a fully standardised solution however it interprets Vertices, Vertex Normals, Texture Coordinates and Face coordinates to load All triangle formatted vewrtex data from Obj files. In this project I then made planet and star models to load textures onto for the orbital simulation.


The first important data structure used in the project is the Scene Graph, which organizes and manages the hierarchical structure of 3D objects in the scene in relation to a parent node defined when creating the scene graph instance. The code snippet below shows the use for this, by allowing for all objects in the graph to be selected at once using a pre order traversal of the structure. In this project this allowed for all planets to also be selected and manipulated when selecting the star object.

The second core data structure is the linked list, which is used throughout the simulation instead of arrays or vectors, to allow for efficient and dynamic memory allocation for linked objects for example when handling the updates or rendering of all objects in the scene. The push node code and Node structure can be seen below.

For this simulation I wanted the ability for the user to be able to select and manipulate individual objects within the scene, this being the planets. For this I implimented a raycasting system using the glut screen coordinates, world position and radius of a given object and depth testing to determine which object to be selected. The raycast code can be seen below with the selection logic itself mostly contained in a separate function to maintain modularity.


Loading and rendering objects was a complicated process as partly outlined in the .obj loader section. One part of loading these objects is texture loading in different formats, below is the RAW texture loader using point sampling which is then wrapped stored via incremental ID and wrapped around the appropriate objects.


Lighting objects graphically required two major elements. The lighting component and the material components. The lighting component is used to determine the direction and position of lights in the scene, whereas the material component is used to determine the way light is refelcted off of the specfiic object the material is applied to.

Scroll to the moon is a 2D sidescrolling retro platformer game built for both Windows and the Evercade EXP. It uses SDL2 and C++ to create a dynamic gameplay loop with a variety of fairly complex mecahnics and features.


SDL uses event based input to detect hardware input events. For this game I needed to ensure input was handled correctly across different platforms. This involved reading joypad inputs, console button inputs, keyboard inputs, and mouse inputs, as all of these are used to replicate the same system of controls across the different devices. The code for menu selction and character control handling can be seen below.


This game uses tilemaps defined using a basic text file format to create the game levels. These tilemaps are initialized at a specific size with a matching text file then used to read this file and create tlies based on known tile mapping rules based on the tile type and collision type of a given tile in the tile map. The code to read these files can be seen below.


The collisions in this game's framework are handled with 3 main types from a collision instance: a box collision, circle collision and tilemap collision. Tile map collision is the most complex requiing a world coordinate to tilemap coordinate. In addition tot his the collision box of both the colliding gameobject and adjacent tiles, to detect a specific collision.


In scroll to the moon there are multiple menu screens and multiple level screens. For this reason a screen manager and multiple game screen classes are implimented and swapped between using custom SDL user events. Instances of these game classes encapsulate instances of gameobjects and other classes in the game to effficiently handle these different screens and textures on each of these screens. Code for the switching and structure of these gamescreens can be seen below.


Enemies in scroll to the moon are implimented as a child of gameobject with collision and movement code between two gameobject points in which enemies are set to move between. The enemy is designed to take a hit from the player on collision to act as a hazard for more interesting gameplay.

This also was updated as tasks were completed ahead of or behind schedule.


While not in charge of every stage of development, I was a key programmer for the development of the main movement, climbing and grappling mechanics throughout various stages of development.
